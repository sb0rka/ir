# Маршрут аналитика SOC

## Этап 0. Вход и обзор (Landing / Queue)

SOC аналитик открывает рабочее место и видит поток событий и корреляций — единую очередь срабатываний из всех подключенных источников.

Эту страницу фронтенд получает непосредственно из Gateway. Полный поток не
копируется в БД Investigations: там оказываются только выбранные аналитиком или
агентом нормализованные копии выбранных данных.

**Таблица срабатываний:** критичность, время, срабатывание, затронутые сущности (хост, пользователь, процесс, адрес), источник (EDR / NDR / SIEM / и другие источники), статус (новое / в расследовании / закрыто).

**Корреляции** визуально выделены: это уже сгруппированные системой события (например, «7 событий с 3 источников по хосту WS-1042»). Раскрываются прямо в таблице — видно, какие события внутри и по какому признаку связаны.

**Единая строка поиска и фильтрации** работает по нормализованной модели данных:

- события всех источников приведены к общим полям (хост, пользователь, процесс, хеш, IP, домен, критичность, источник), поэтому один запрос ищет сразу по EDR, NDR, SIEM и другим источникам;
- паттерн чипов-фильтров: клик в строку → список полей → автокомплит значений из фактических данных → фильтр становится чипом (`хост: WS-1042 ×`); несколько чипов через AND, несколько значений в чипе через OR;
- диапазон времени — отдельный контролом с пресетами; набор фильтров можно сохранить как представление;
- клик по сущности открывает её карточку; действие **«Найти связанные»** добавляет соответствующий фильтр;
- тот же компонент строки используется везде: в глобальной очереди, в контексте расследования.

**Быстрый старт** — действие **«Начать расследование»** непосредственно из очереди.

> **Ключевое действие этапа:** провести первичную оценку и выделить срабатывания, требующие детального расследования.

---

## Этап 1. Начало расследования

Аналитик выбирает корреляцию (или одно событие, или несколько через мультиселект) и нажимает «Начать расследование»:

- создаётся контекст расследования — открывается новый таб; у расследования фиксируется родитель: поток событий (или другое расследование — см. этап 4);
- фронтенд создаёт расследование запросом `POST /api/v1/investigations`; в нём
  передаются только название, описание, родительское расследование и рабочие
  пространства SOM;
- получив идентификатор расследования, фронтенд отдельным запросом
  `POST /api/v1/investigations/{id}/context` передаёт коды источников и исходные
  идентификаторы выбранных событий и сущностей; сервис расследований сам
  получает их актуальные данные и связи через Gateway, сохраняет их и строит
  начальный подтверждённый граф;
- после сохранения контекста фронтенд сам запускает **«Насыщение контекста»** — фоновые задачи ИИ-агента отображаются в боковой панели и не блокируют дальнейшую работу; повторный запуск остаётся ручным;

---

## Этап 2. Обогащение и насыщение контекста

ИИ-агент читает прикреплённые события, сущности и граф через Investigation MCP,
а дополнительное evidence ищет через его read-only `gateway_*` tools. Для
временного demo-flow OpenCode получает пользовательский JWT через `ACCESS_KEY`;
`ir-api` server-side передаёт тот же bearer и обязательный project scope в
Gateway. Через
`add_investigation_agent_results`
агент передаёт локальные UUID либо выбранные source references. В запрос также
входят выбранные для графа узлы и связи,
обоснование, степень уверенности и подтверждающие события; `som_issue_ids`
связывают результат с исследовательской задачей.

Только явно перечисленные агентом nodes/edges отображаются на графе. Ноды
получают origin `agent`, рёбра — status `proposed`, поэтому новые результаты
визуально отделяются от подтверждённого аналитиком контекста.

**Каждый результат содержит:**

- событие, сущность или найденную связь;
- обоснование: по какому признаку связано («тот же хеш на хосте SRV-DC01», «исходящее соединение процесса к тому же IP»);
- исходные данные и источники, на которых основан результат;

Аналитик **подтверждает** результат — он становится частью подтвержденного контекста расследования — либо **отклоняет** его.

При необходимости аналитик запускает дополнительную проверку для выбранного события, сущности или находки. Новая задача выполняется в фоне и дополняет текущее расследование.

**Ручное добавление событий** выполняется поиском в Gateway.

## Этап 3. Работа с контекстом

Контекст расследования — таб с переключателем представлений.

### Табличное представление

- все сохранённые события контекста единым списком: время, источник, тип,
  сущности, происхождение (`attached_by=analyst|agent`);
- сортировка, фильтрация, группировка по сущности;
- подтверждение или отклонение предложенных результатов и фиксация находок.

### Граф + таймлайн (совмещённые)

- **граф:** узлы — сущности (хост, пользователь, процесс, файл, адрес), рёбра — связи с типом («запустил», «соединился», «аутентифицировался»);
- **таймлайн** под графом: события во времени; выбор диапазона на таймлайне подсвечивает/фильтрует граф;
- клик по узлу графа → карточка сущности (боковая панель): историчность, окружение, связанные артефакты, действия («обогатить», «проверить репутацию», «добавить в находки»);
- предложенные агентом, но ещё не принятые элементы отображаются на графе призрачно/пунктиром — принять/отклонить можно прямо там.

**Действия с артефактами** (из карточки или контекстного меню): проверка репутации IP/хеша, декодирование base64/URL, отправка в песочницу — результат проверки и его источник возвращаются в контекст расследования.

## Этап 4.Постановка исследовательских задач

Для исследования находок на графе аналитик работает с карточками **issues** — отдельные исследовательские задачи, связанные с контекстом расследования.

- **Issue** описывает, что необходимо исследовать, и содержит задание для ИИ-агента.
- Issue может быть привязан к одной или нескольким нодам графа. Для одной ноды может существовать несколько разных исследовательских задач.
- **Sub-issue** — отдельный проверяемый шаг или гипотеза внутри issue. Sub-issues также могут содержать самостоятельные задания для агентов.
- Одинаковые типы задач могут запускаться для разных нод, например проверка присутствия одного хеша на нескольких хостах.
- Результаты выполнения возвращаются в контекст расследования и могут добавлять новые события, связи и находки на граф.
- **Комментарии** к issue и sub-issue используются аналитиком для фиксации заметок и обоснований.

Таким образом, граф хранит фактический контекст расследования, а issues и sub-issues — задачи и гипотезы, с помощью которых этот контекст исследуется и расширяется.

## Этап 5. Реконструкция и оценка распространения

- **Назад во времени:** от подтверждённого вредоносного процесса — цепочка родительских процессов до точки входа (фишинговое письмо, эксплойт), визуально на графе.
- **Вширь:** в очереди расследования аналитик добавляет чип `хеш: <IOC>` (или адрес) без ограничения по хостам — очередь показывает все узлы с этим признаком; найденные принимаются в контекст → перечень затронутых узлов.

---

## Этап 6. Ветвление

- **Дочернее расследование:** обнаружена побочная линия (например, второй скомпрометированный хост с другим способом проникновения) → аналитик выделяет часть сущностей, создаёт дочернее расследование и отдельным запросом добавляет в него выбранный контекст. Родителем нового расследования становится текущее.
- Несколько параллельных расследований = несколько табов; переключение без потери состояния.
