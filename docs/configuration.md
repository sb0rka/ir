# Конфигурация проекта IR

Откройте «Конфигурация», выберите проект и разрешите Platform API доступ к конфигурации. В редактор загружается один проектный секрет `IR/SOURCE_CONFIGURATION` из sb0rka. Он общий для пользователей проекта с соответствующими правами; выбранный проект остаётся контекстом работы браузера.

```json
[
  {
    "name": "pt-maxpatrol-siem",
    "CorePortalCookie": "cookie-value",
    "idsrv.session": "session-value",
    "idsrv": "identity-value",
    "IncidentManagementPortalCookie": "portal-value"
  },
  {
    "name": "pt-nad",
    "sessionid": "nad-session",
    "csrftoken": "nad-csrf"
  }
]
```

Конфигурация — массив объектов. Каждый источник имеет непустое строковое поле `name`; имена источников уникальны. Остальные поля — произвольные строки. Пустой массив `[]` сохраняет пустую конфигурацию. Исходный JSON сохраняется и загружается без переформатирования: отступы, пробелы, переносы, порядок ключей и escape-последовательности остаются как переданы. Имена и значения не обрезаются. Дубли ключей и имён источников, вложенные credentials, null и нестроковые значения отвергаются. Компактное JSON-представление ограничено в IR 64 КиБ; sb0rka проверяет только общий синтаксис JSON для `payload_kind: json`. Для тела запроса действует отдельный лимит 512 КиБ.

Каждое успешное сохранение заменяет весь документ и создаёт новую версию. Отсутствующий источник или ключ удаляется из новой версии. Используется обычное создание версий Secrets: последний успешно сохранённый документ становится текущим. Клиент не передаёт номер прочитанной версии. Уникальность секрета обеспечивает существующее ограничение `(project_id, name)`. «Перечитать» загружает актуальное значение. История сохраняется в механизме версий Secrets; откат в интерфейсе IR пока не предоставляется.

Старые `IR_CONFIG` и `DEMO_*` секреты не импортируются, не изменяются и не удаляются. Новые значения находятся в памяти открытого редактора, не сохраняются в localStorage/IndexedDB/sessionStorage и очищаются при его закрытии или смене контекста.

## Полномочия

IR продолжает использовать клиента `sb0rka-ir-web`. Для аудитории `sb0rka-api` добавлены `secrets.read`, `secrets.reveal`, `secrets.create` и `secrets.write`; consent Gateway остаётся независимым. Существующие grants не получают эти scopes автоматически: нужен повторный consent через «Изменить доступ»/«Разрешить конфигурацию».

Scopes разделены: `secrets.read` — список, метаданные и версии без значения; `secrets.reveal` — значение; `secrets.create` — создание; `secrets.write` — новая версия. Для списка сохранена совместимость с `secrets.write` SOM; в регистрации маршрута это явный `anyOfScopes{read, write}`. Для чтения JSON IR нужны read и reveal; сохранение требует read/create/write и не требует reveal. API проверяет живую сессию, grant/version, проекты и действующий пользовательский RBAC: reveal для чтения, secret.create для создания и secret.version.create для обновления. Scope не расширяет роль пользователя. Ограничения SOM на ключи агентов сохранены. IR сам выбирает имя `IR/SOURCE_CONFIGURATION`, задаёт `payload_kind: json` и проверяет свою схему. sb0rka проверяет только общий синтаксис JSON и шифрует исходную строку. При сохранении IR идемпотентно прикрепляет тег `source:ir` через существующий Tags API, без изменения цвета общих тегов. Ошибка установки тега не скрывается; для обновления версия создаётся только после успешной установки тега. Создание секрета и установка тега — отдельные операции API: если тег не удалось добавить после создания, повторное сохранение использует уже созданный секрет.

Интерфейсы Platform API:

- `GET /projects/{project_id}/secrets` — поиск имени и текущей версии;
- `POST /projects/{project_id}/secret` — обычный секрет с `payload_kind: json` и исходным документом в строке `secret_value`;
- `POST /projects/{project_id}/resources/{secret_public_id}/secret/versions/{version}/reveal` — текст конкретной версии;
- `POST /projects/{project_id}/resources/{secret_public_id}/secret/versions` — строка `secret_value`;
- `POST /projects/{project_id}/resources/{secret_public_id}/tag` — `{"tag_key":"source","tag_value":"ir"}` с текущими scope и RBAC для прикрепления тега.

Dashboard вызывает только `GET/PUT /api/v1/configuration` IR API с `X-Project-ID`. PUT принимает сам JSON-массив источников без служебной обёртки. GET возвращает метаданные и строку `value` с исходным документом; если секрета ещё нет, `value` равно `[]`. Ответы конфигурации имеют `Cache-Control: no-store`; значения не включаются в ошибки и журналы.

## Gateway

Для пользовательского запроса IR API получает у Auth два независимых delegated JWT. `Authorization` содержит токен для `sb0rka-ir-gateway`; `X-IR-Config-Token` — Bearer JWT для `sb0rka-api` ровно с `secrets.read` и `secrets.reveal`. IR заменяет оба заголовка, поступившие от клиента. Gateway проверяет совпадение sub/sid/client/actor и разрешённый проект.

Каждый пользовательский запрос проходит Gateway introspection и проверку текущих прав чтения конфигурации в Platform API, включая ответы с метаданными источников. При недоступности обязательной проверки операция закрывается. IR использует API-токен для общих Secrets routes, выбирая только `IR/SOURCE_CONFIGURATION`; вендору передаётся только Cookie, собранная из известных полей объекта с соответствующим `name`. Поля другого источника для этого не используются. Прочие JSON-поля, JWT и внутренние заголовки вендору не передаются.

Plaintext credentials не кешируются между запросами. Внутри одного входящего запроса все адаптеры используют один согласованный snapshot JSON. Неполный или недопустимый набор cookie делает соответствующий источник недоступным. Явно заданная пустая строка передаётся как `CookieName=` и отличается от отсутствующего поля; принимает ли её источник, определяет его ответ. Адреса источников задаются серверной конфигурацией; доступность определяется credentials проекта. Панель в JSON-редакторе строит список по `name` сохранённой конфигурации, показывает статусы Gateway и сохраняет в списке неподключённые источники. Статусы обновляются после сохранения и по кнопке «Проверить».

## Ключ доступа агента

В блоке доступа агента нажмите «Сгенерировать». IR создаёт текстовый секрет `IR/AGENT_ACCESS` в Platform Secrets и сохраняет в своей БД только его SHA-256, UUID/версию и маску. Ключ длиной 64 символа с префиксом `s0_ir_agent_` показывается один раз до закрытия блока, смены проекта или перезагрузки страницы. Повторно значение можно посмотреть в обычном интерфейсе Platform Secrets.

В SoM добавьте `SB0RKA_IR_AGENT_TOKEN` в переменные окружения исполнителя. Карточка MCP «Sb0rka IR» вставляет remote-конфигурацию с `Bearer {env:SB0RKA_IR_AGENT_TOKEN}`; укажите URL `/mcp` своего IR и `X-Project-ID`. Для REST используется тот же Bearer и заголовок проекта. Ключ открывает доменные операции проекта, но не управление конфигурацией, ключами и OIDC.

Запись результатов через MCP и REST выбирает расследование по `investigation_id`, а при необходимости гипотезу по `hypothesis_id`. Привязка к SoM issue не требуется. Автор записи определяется сервером по проверенному удостоверению; существующие связи с SoM в исторических данных сохраняются.

«Ротация» создаёт следующую версию Platform-секрета и активирует новый хеш. Старый ключ сразу отклоняется IR и Gateway, даже если его версия доступна в истории Secrets. После ротации обновите env и перезапустите исполнитель или MCP-подключение. Хеш проверяется в БД на каждом запросе, без кеша и вызовов `reveal`.

Для агентских запросов IR передаёт тот же Bearer в Gateway без обмена JWT и без `X-IR-Config-Token`. Gateway независимо проверяет ключ и использует AES-256-GCM-копию `IR/SOURCE_CONFIGURATION` в БД IR, привязанную к проекту через AAD. Она обновляется при сохранении или «Перечитать» через IR. Прямое редактирование или удаление секрета в Platform подхватывается после перечитывания; старый ответ не перезаписывает новую конфигурацию. При недоступности БД или серверной конфигурации агентский Gateway возвращает `503`, без переключения на пользовательскую сессию. Logout, истечение пользовательского JWT и перезапуск процессов не влияют на агентский доступ.

`IR_GATEWAY_CONFIGURATION_KEY` — отдельный base64-ключ на 32 байта, общий для IR API и Gateway. Он должен отличаться от session/OIDC-ключей. Gateway получает `DATABASE_URI` существующей БД IR; Platform Secrets остаётся основным хранилищем исходной конфигурации.

## Запуск без источников и VPN

Обычный `docker-compose.yml` не содержит OpenVPN. Пустые `SOURCE_PT_*_BASE_URL` и `SOURCE_PT_NAD_STORE_IDS` в `apps/gateway/.env` запускают Gateway без источников; авторизованный `/api/v1/sources` возвращает `{"items":[]}`. Ручная карта project/source не нужна.

Чтобы включить источник, настройте его URL и необходимые server-owned параметры, затем сохраните его credentials в `IR/SOURCE_CONFIGURATION` проекта. SIEM требует оба URL, NAD — URL и store IDs. Частично заданные параметры вызывают явную ошибку запуска. Источник появляется для проекта только при наличии допустимого набора Cookie; при удалении credentials исчезает на следующем запросе без перезапуска Gateway. Статус backend может кешироваться, доступ по credentials перепроверяется всегда. Запрос к ненастроенному источнику отвергается без внешнего обращения. URL и store IDs из JSON не используются.

```sh
docker compose config --quiet
docker compose --profile apps up -d --build ir-api gateway
```

Нужны работающая PostgreSQL IR, миграции `011-auth_sessions.sql` и `012-agent-access.sql`, те же `SB0RKA_IR_WEB_CLIENT_SECRET` и `SB0RKA_IR_GATEWAY_CLIENT_SECRET`, что у Auth, и три независимых AEAD-ключа в `apps/investigations/.env`. Ротация refresh handles входит в `011-auth_sessions.sql`. Каждый AEAD-ключ: `head -c 32 /dev/urandom | base64 -w0`. `IR_GATEWAY_CONFIGURATION_KEY` и `DATABASE_URI` передаются также Gateway. Общие ключи Auth не генерировать заново.

Issuer должен точно совпадать с discovery действующего Auth. В проверенном локальном окружении это `http://192.168.44.129:8020`, `MAX_ACCESS_TOKEN_TTL_SEC=3600`, skew — 30 секунд. Callback/Web URL — `http://localhost:8090` и `http://localhost:5174`. HTTP разрешён только явной dev-настройкой. Перед использованием с другого компьютера согласуйте browser origin и зарегистрированные callbacks.

В sb0rka применяется адресная миграция `seed/012-ir_secret_permissions.sql` и обновляются необходимые Auth/API. Для загрузки новой политики нужен актуальный процесс Auth. SOM и его ключи/сервисы не перезапускаются. VPN при наличии отдельной конфигурации доступен через дополнительный `docker-compose.vpn.yml`; для текущего запуска он не используется.

Локальный refresh handle IR ротируется с 30-секундным повтором потерянного ответа; обнаруженный повтор предыдущего handle после окна отзывает эту сессию. Абсолютный deadline Auth не продлевается. Обновление поддерживает существующие локальные сессии. Интеграция IR → SOM остаётся отключённой в этом этапе.
