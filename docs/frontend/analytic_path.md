# Маршрут аналитика SOC

## Этап 0. Вход и обзор (Landing / Queue)

Аналитик первой линии открывает рабочее место и видит поток событий и корреляций — единую очередь срабатываний.

**Таблица срабатываний:** severity, время, правило корреляции, затронутые сущности (хост, пользователь, процесс, адрес), источник (EDR / NDR / SIEM / UEBA), статус (новое / в расследовании / закрыто).

**Корреляции** визуально выделены: это уже сгруппированные системой события (например, «7 событий с 3 источников по хосту WS-1042»). Раскрываются inline — видно, какие события внутри и по какому признаку связаны.

**Единая строка поиска и фильтрации** по всем источникам — один механизм вместо четырёх языков запросов:

- работает по нормализованной схеме единого хранилища: события всех источников приведены к общим полям (хост, пользователь, процесс, хеш, IP, домен, severity, источник), поэтому один запрос ищет сразу по EDR, NDR, SIEM и UEBA;
- паттерн чипов-фильтров: клик в строку → список полей → автокомплит значений из фактических данных → фильтр становится чипом (`хост: WS-1042 ×`); несколько чипов = AND, несколько значений в чипе = OR;
- свободный текст с типизацией ввода: система распознаёт формат (IP, хеш, домен, имя) и сама подставляет нужные поля — аналитику не нужно знать схему;
- диапазон времени — отдельный контрол с пресетами; наборы чипов можно сохранять как типовые фильтры триажа;
- любая сущность в любом месте интерфейса кликабельна → «найти все события» с автоподстановкой чипа — главный источник экономии кликов;
- тот же компонент строки используется везде: в глобальной очереди, в контексте расследования, в очереди расследования (см. этап 3а).

**Быстрая квалификация** прямо из очереди: «False Positive» (закрыть с причиной) или «Начать расследование».

> **Ключевое действие этапа:** триаж — за минимальное число кликов отсеять шум и выделить то, что требует расследования.

---

## Этап 1. Начало расследования

Аналитик выбирает корреляцию (или одно событие, или несколько через мультиселект) и нажимает «Начать расследование»:

- создаётся контекст расследования — открывается новый таб; у расследования фиксируется родитель: поток событий (или другое расследование — см. этап 5);
- в контекст автоматически попадают исходные события и извлечённые из них сущности (хост, пользователь, процесс, хеш, IP) — это «seed» контекста;
- система автоматически ставит задание ИИ-агенту на обогащение — статус видно в интерфейсе («Агент ищет связанные события…»);
- аналитик тем временем уже может работать: смотреть исходные события, карточки сущностей, очередь расследования.

---

## Этап 2. Обогащение и модерация предложений

*Ядро сценария.*

ИИ-агент возвращает предложения — кандидатов на включение в контекст. Они появляются в очереди расследования (этап 3а) как верхний слой, отсортированный по релевантности.

**Каждое предложение содержит:**

- событие или сущность;
- обоснование: по какому признаку связано («тот же хеш на хосте SRV-DC01», «исходящее соединение процесса к тому же IP», «UEBA: аномальный вход этого пользователя за 20 минут до алерта»);
- оценку уверенности; при неполных или противоречивых данных — явный статус неопределённости (ТЗ п. 6.3).

Аналитик **принимает** (сущность/событие входит в контекст, появляется на графе и в таблице) или **отклоняет** (приглушается, решение журналируется — аудит и воспроизводимость по ТЗ п. 5.14).

Принятая сущность триггерит новый цикл обогащения — агент дообогащает контекст вокруг неё, а контекстный фильтр очереди автоматически расширяется.

**Ручное добавление событий** — прямо из очереди расследования в один клик, либо через единый поиск из любого места системы («добавить в расследование» на любом событии).

---

## Этап 3. Работа с контекстом

Контекст расследования — таб с переключателем представлений.

### Табличное представление

- все события контекста единым списком: время, источник, тип, сущности, кем добавлено (агент / аналитик / seed);
- сортировка, фильтрация, группировка по сущности;
- отсюда — квалификация отдельных событий и фиксация находок.

### Граф + таймлайн (совмещённые)

- **граф:** узлы — сущности (хост, пользователь, процесс, файл, адрес), рёбра — связи с типом («запустил», «соединился», «аутентифицировался»);
- **таймлайн** под графом: события во времени; выбор диапазона на таймлайне подсвечивает/фильтрует граф;
- клик по узлу графа → карточка сущности (боковая панель): историчность (типична ли активность), окружение, связанные артефакты, действия («обогатить», «проверить репутацию», «добавить в находки»);
- предложенные агентом, но ещё не принятые элементы отображаются на графе призрачно/пунктиром — принять/отклонить можно прямо там.

**Действия по артефактам** (из карточки или контекстного меню): проверка репутации IP/хеша, декодирование base64/URL, отправка в песочницу — вердикт возвращается в контекст.

---

## Этап 3а. Очередь событий расследования

Кроме контекста, в табе расследования есть своя очередь событий — сворачиваемая нижняя панель. Это не копия глобальной очереди, а «линза» на общий поток, привязанная к расследованию.

- **Контекстный фильтр** собирается автоматически из сущностей контекста (`хост IN (…) OR пользователь = … OR хеш = …`) и живёт вместе с контекстом: принял новую сущность — очередь тут же расширилась событиями по ней.
- **Поверх** — сохранённые фильтры расследования: аналитик добавляет свои чипы (severity, источник, окно атаки), они хранятся в расследовании и видны при передаче коллеге.
- **Live-режим:** новые события, попадающие под фильтр, доезжают в очередь по мере поступления; в свёрнутом состоянии панель показывает счётчик («12 новых релевантных»). Для активной атаки — способ видеть продолжение активности, не выходя из таба.

**Метки отношения к контексту** для каждого события:

| Метка | Описание |
|-------|----------|
| в контексте | принято в расследование |
| предложено агентом | с обоснованием, accept/reject |
| релевантно | совпадает с фильтром, не оценено, с индикатором степени совпадения |
| отклонено | приглушено |
| в другом расследовании | ссылка на тот таб |

Hover по событию в очереди → на графе подсвечиваются сущности, которые оно затронет: аналитик видит, куда событие «встанет», до принятия.

Визуально очередь жёстко отделена от контекста: **контекст** — принятое и проверенное, **очередь** — сырые кандидаты.

---

## Этап 4. Фиксация находок

По ходу расследования аналитик ведёт журнал находок:

- любое событие/сущность/вердикт помечается как находка с комментарием;
- журнал — хронология выводов аналитика, привязанная к расследованию (замена «блокнота»);
- подсказки следующих шагов (правила или ИИ): «проверьте другие хосты с этим хешем», «постройте цепочку процессов назад во времени».

---

## Этап 5. Ветвление и эскалация

- **Дочернее расследование:** обнаружена побочная линия (например, второй скомпрометированный хост с другим вектором) → аналитик выделяет подмножество сущностей и создаёт дочернее расследование — новый таб, родитель — текущее расследование. Контекст-seed наследуется из выделенного.
- **Эскалация на вторую линию:** передача расследования (роли по ТЗ п. 5.13), контекст полностью сохранён — принимающий видит граф, таймлайн, находки, фильтры очереди и журнал решений accept/reject.
- Несколько параллельных расследований = несколько табов; переключение без потери состояния.

---

## Этап 6. Реконструкция и оценка распространения

*Вторая линия.*

- **Назад во времени:** от подтверждённого вредоносного процесса — цепочка родительских процессов до точки входа (фишинговое письмо, эксплойт), визуально на графе.
- **Вширь:** в очереди расследования аналитик добавляет чип `хеш: <IOC>` (или C2-адрес) без ограничения по хостам — очередь показывает все узлы с этим признаком; найденные принимаются в контекст → перечень затронутых узлов.

---

## Этап 7. Завершение: пакет реагирования и отчёт

**Панель пакета реагирования:** аналитик отбирает артефакты из находок (тип + узел: «хеш X — заблокировать», «хост Y — изолировать»), формирует структурированный пакет для EDR/IRP. Критичные действия — только с явным подтверждением (human-in-the-loop).

**Отчёт:** система собирает описание инцидента из контекста — хронология, затронутые сущности, находки, решения; опционально ИИ генерирует связный текст, аналитик редактирует и экспортирует.

Расследование закрывается с вердиктом (True Positive / False Positive / Benign) — статус виден в родительском потоке.

---

## Сквозной пример (демо-сценарий, ТЗ п. 10)

1. В очереди — корреляция «Подозрительный PowerShell + исходящее соединение на редкий домен» по хосту WS-1042 (EDR + NDR).
2. Аналитик открывает расследование → таб с контекстом, агент запущен, очередь расследования уже отфильтрована по WS-1042.
3. Агент предлагает: событие входа пользователя j.smith с нетипичного IP (SIEM), аномалию поведения (UEBA), тот же хеш на SRV-FILE01 (EDR). Аналитик принимает первые два — очередь расширяется событиями по j.smith; третье принимает и разворачивает в дочернее расследование по SRV-FILE01.
4. Проверка репутации домена → C2. Хеш → в песочницу → вердикт «троян». Всё фиксируется в находках.
5. На графе восстанавливается цепочка: письмо → вложение → PowerShell → C2; таймлайн показывает 40 минут активности. В live-очереди тем временем появляются 3 новых события по C2-адресу — принимаются в контекст.
6. Пакет реагирования: изолировать WS-1042, заблокировать домен и хеш, сбросить пароль j.smith. Отчёт экспортирован.
