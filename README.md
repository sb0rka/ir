# Incident Response

Платформа расследования киберинцидентов: единый рабочий стол аналитика поверх
разрозненных источников (SIEM, EDR, NDR, инфраструктурные логи).

Продукт держится на одном тезисе: **любая связь и любой вывод доказуемы ссылкой
на исходное событие**. Отсюда устройство схемы и инварианты ниже.

## Структура

```
ir/
├── api/                      OpenAPI — источник правды контракта
│   ├── openapi.yaml          корень: карта путей, теги, безопасность
│   ├── components/           параметры, ответы, схемы по доменам
│   ├── paths/                ручки, сгруппированы по ресурсу
│   ├── bundle.yaml           собранный файл (генерируется, коммитится)
│   └── bundle.py             сборка и валидация
├── apps/
│   └── investigations/       Go-сервис: cmd/api + cmd/worker
├── packages/
│   ├── contract/             Go-типы и серверные интерфейсы (генерируются)
│   └── contract-ts/          TypeScript-типы и клиент (генерируются)
├── db/migrations/            SQL-миграции схемы inv
└── tools/                    вспомогательная генерация
```

## Контракт первичен

Спека в `api/` — источник правды. Из неё генерируются:

- **Go**: типы, `StrictServerInterface`, роутер (`oapi-codegen`) → `packages/contract`;
- **TypeScript**: типы и типизированный клиент (`openapi-typescript` + `openapi-fetch`) → `packages/contract-ts`.

Руками ни то, ни другое не правится: меняешь спеку, запускаешь `task generate`.
Оба артефакта коммитятся — компилятор Go и клиентские сборки не должны
зависеть от установленного генератора.

```bash
task spec         # валидация спеки + сборка api/bundle.yaml
task generate     # перегенерировать Go и TypeScript
task build        # собрать бинари в bin/
task check        # то, что гоняет CI
```

Нереализованные ручки отвечают `501` — заглушки генерируются из интерфейса
(`tools/gen_unimplemented.py`), так что новая ручка в спеке не ломает сборку,
а честно сообщает, что её ещё нет.

## Локальный стенд

```bash
task dev          # Postgres + миграции + api + worker
curl localhost:8090/healthz
task dev-down
```

Без публичного ключа платформы (`ACCESS_TOKEN_PUBLIC_KEY_FILE_PATH`) сервис
поднимется и ответит на `/healthz`, но запросы с токеном получат 401 — так
неполный конфиг стенда виден сразу, а не притворяется рабочим.

В dev-стенде `INV_DEFAULT_ROLE=l2`: любой залогиненный ведёт расследования,
чтобы не раздавать роли руками. В проде переменная пуста — запрет по умолчанию.

## Модель данных

Три категории, и они не смешиваются:

| | Что это | Свойства |
|---|---|---|
| **События** | факты источников | неизменяемы, без статусов, только цитируются |
| **Сущности** | узлы, пользователи, процессы, адреса, хеши | идентичность, обогащается, не отклоняется |
| **Расследования** | гипотезы и выводы | дерево через `parent_id`, вердикт, проходят ревизию |

Отдельной сущности «находка» нет: гипотеза — это под-расследование со своим
вердиктом. Граф строится на `graph_nodes` (сущность или событие) и `edges`
между ними; тип связи проверяется справочником `relation_types`.

Инварианты, которые держит база:

- улика цитируется только внутри своего расследования — составной внешний ключ
  `(event_id, investigation_id)`;
- узел графа ссылается ровно на одну сущность или одно событие, и тип совпадает
  с объявленным;
- одна сущность в расследовании — один узел, иначе рёбра расщепляются;
- повторный прогон правил и агента не плодит дубли рёбер;
- закрытое расследование обязано иметь вердикт, отклонённое — причину.

Инварианты уровня сервиса: под-расследование нельзя подтвердить без хотя бы
одной улики; связь от агента обязана нести обоснование и основания; ревизия
батчем применяется целиком или никак.

## Интеграции

- **sb0rka** — идентификация (Ed25519 JWT), тенант (`project_id`), управляемый
  Postgres. Роли SOC (`l1`, `l2`, `lead`, `admin`) свои: платформенные
  owner/admin/editor/viewer описывают другое.
- **SOM** — исполнение агентов и канбан. Расследование связывается с
  workflow, узел графа — с исследовательской задачей. Ссылки без внешних
  ключей: другая база, целостность на сервисе.

## Разработка

Слои строгие: `transport` → `server` → `store` → `domain/model`. Единственная
дверь к базе — интерфейс `store.Database`; новый запрос это метод интерфейса
плюс реализация с SQL инлайном. Ошибки — типизированные, транспорт разворачивает
их в конверт `{"error": {"code", "message", "details?"}}`.
